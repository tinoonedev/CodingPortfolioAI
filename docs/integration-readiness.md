# Integration readiness contract

This document defines the minimum production contract for connecting Fieldwork to external services. The app has a real Jira OAuth project connection and a partial OpenAI credential/readiness path; Figma, GitHub delivery, and deployment integrations are not implemented. Do not report an external action as complete unless the service confirms it.

Before implementation, assign a named product owner and technical owner, confirm the target account/project/repository, verify each permission against the exact API endpoint, and record the credential owner and rotation process. Keep credentials server-side in a managed secret store. Never place tokens in browser storage, source control, prompts, or logs.

## Cross-integration requirements

- Store credentials in a managed secret store, scope them to a project or installation, rotate them, and provide revocation instructions.
- Use OAuth `state` and exact registered redirect URIs for browser authorization flows. Keep access/refresh tokens out of the browser and redact authorization headers.
- Record append-only audit events for externally visible reads and writes. Include actor, target, operation, correlation ID, timestamp, and provider result while minimizing personal or customer data.
- Distinguish permission errors, validation errors, rate limits, transient outages, and ambiguous timeouts. Never silently fall back to seeded data or fabricated success.
- Define idempotency, bounded retry, reconciliation, and recovery behavior for each write before enabling it.
- Verify integration tests against a dedicated real test tenant/repository when available. Tests must clearly identify when credentials or an external service are unavailable; they must not substitute a mock and label it end-to-end coverage.
- Treat every task as scoped to a selected Jira issue, but do not require a task-wide Jira comment gate to begin work. Obtain explicit authorization for sensitive Jira writes and validate the selected site, project, and issue before executing them.

### OpenAI agent runtime rollout

- Workspace owners can save an OpenAI project key in PostgreSQL after server-side model pricing and an encryption keyring are configured. AES-256-GCM binds the encrypted credential to its workspace and project; raw keys are not returned, logged, or passed into the browser's persistent storage. The save is audited and does not contact OpenAI or validate that the key is active.
- The authenticated project panel reports missing setup and rejects agent task starts with OPENAI_SETUP_REQUIRED. Even after project configuration, the run endpoint returns execution unavailable until a reviewed live Responses adapter is enabled. There is no process-wide key fallback, seeded response, or fake successful run.
- Do not report a provider run as ready until a server-side, project-bound credential, explicit model allowlist, positive budget, request limit, and enforceable model pricing policy can be loaded and audited for that project.
- Initial generations must use the Responses API with tools disabled and provider response storage disabled. This only disables Responses application-state storage; account-level abuse monitoring may still retain submitted content under the account's default controls. Show this retention disclosure before allowing client content to be sent.
- Persist a run only after validated provider output. Store project, role, model, provider request ID, timestamps, sanitized outcome, token/cost metadata where available, and artifact; never log raw prompts, output, provider error bodies, authorization headers, or key material.
- Before any execution path can create a `running` row, add a bounded lease/recovery process: an expired in-flight run becomes `unknown`, retains its reservation, and is never automatically retried. Reconciliation must use authoritative provider evidence and apply settlement or release exactly once; until that path exists, no run rows or provider requests may be created.
- Reserve the maximum permitted request cost against the project's budget before sending. Reject if the cost cannot be bounded from the trusted model pricing policy. Do not blindly retry ambiguous timeouts. Only add bounded retries for documented transient failures before any side effect exists.
- Do not treat UTF-8 bytes as model tokens when estimating spend. The reservation must use a trusted model-specific token upper bound for the complete serialized request, including agent instructions and any structured-output schema. Enforce the project's byte limit before tokenization.
- Keep the adapter disabled until the payload boundary and destination are explicitly approved, budget reservation and settlement are implemented, and a live dedicated-project acceptance run succeeds. Re-review the published model prices before updating the server pricing allowlist; never trust prices supplied by the browser.
